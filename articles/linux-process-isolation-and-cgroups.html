Process Isolation and Resource Management with systemd and cgroups v2

Published: November 2026 Category: Linux Internals Reading Time: 9 min

Running production workloads on shared Linux hosts requires deterministic resource bounds. Without strict isolation, an errant database query or a memory leak in a background worker can exhaust page caches, trigger the Linux Out-Of-Memory (OOM) killer indiscriminately, and degrade latency across co-located services.

With the migration from the legacy cgroups v1 multi-hierarchy model to the unified cgroups v2 hierarchy, Linux kernel developers solved the long-standing cross-controller synchronization issues. Combined with modern systemd resource controllers, administrators can enforce strict CPU, memory, and I/O budgets without container virtualization overhead.

1. The Unified Hierarchy Advantage

In cgroups v1, each resource controller (CPU, memory, blkio, pids) operated in its own independent filesystem hierarchy. A process could belong to one hierarchy for CPU scheduling and a completely different branch for memory tracking. This caused severe synchronization anomalies, particularly around writeback cache tracking: dirty memory pages could not be properly mapped back to the I/O cgroup responsible for originating them.

Cgroups v2 enforces a single, unified process tree. Every process in the system belongs to exactly one cgroup node, and resource controllers are enabled hierarchically from root to leaves via cgroup.subtree_control.

Verifying Unified Hierarchy

You can verify whether your system uses the unified hierarchy by running:

findmnt -t cgroup2 /sys/fs/cgroup

If mounted at /sys/fs/cgroup, cgroups v2 is active globally.

2. Memory Control: Throttling vs. Termination

Cgroups v2 introduced a vital distinction between hard termination thresholds and proactive memory reclamation:

  • MemoryMax (kernel: memory.max): The absolute ceiling. If a cgroup exceeds this limit and anonymous memory cannot be reclaimed to swap, the kernel invokes the OOM killer against processes inside that specific cgroup.
  • MemoryHigh (kernel: memory.high): The throttling threshold. When exceeded, processes inside the cgroup are throttled and forced into synchronous direct memory reclamation, while co-located services on the server remain unaffected.
  • MemoryMin (kernel: memory.min): A hard guarantee beneath which page cache and anonymous pages are never reclaimed by global memory pressure. 
# /etc/systemd/system/app-backend.service.d/override.conf
[Service]
# Graceful throttling boundary at 1.8 GB
MemoryHigh=1800M

# Hard boundary at 2.0 GB (triggers cgroup-scoped OOM)
MemoryMax=2G

# Protect 256 MB of baseline runtime working set
MemoryMin=256M

# Restrict maximum concurrent thread count
TasksMax=512

3. Fair CPU Allocation and Hard Caps

CPU management in cgroups v2 supports two distinct operational models: proportional weight distribution and strict period-based quotas.

Weight-based sharing (CPUWeight): Values range from 1 to 10,000 (default: 100). When CPU contention occurs, cycles are distributed proportionally according to weights. If other cores are idle, a service with CPUWeight=50 can still utilize 100% of available CPU.

Hard Bandwidth Caps (CPUQuota): Defines the absolute percentage of CPU time allowed per scheduling period. For example, CPUQuota=150% allows up to 1.5 CPU cores of execution time regardless of server load.

Directive cgroups v2 Kernel File Behavior
CPUWeight=200 cpu.weight Proportional fair-share when host is under load
CPUQuota=80% cpu.max Hard ceiling; throttles execution when budget is depleted
IOWeight=50 io.weight Proportional block I/O bandwidth allocation
IOReadBandwidthMax=/var 10M io.max Enforces maximum disk read throughput

4. Structuring systemd Slices

Rather than configuring limits per individual unit, production servers benefit from dividing workloads into hierarchical slices:

  • system.slice: System daemons, monitoring, and SSH access.
  • production.slice: Primary customer-facing web and API services.
  • background.slice: Batch processors, log shipping, and automated maintenance jobs.
# /etc/systemd/system/background.slice
[Unit]
Description=Background Batch and Maintenance Slice
Before=slices.target

[Slice]
CPUWeight=20
CPUQuota=100%
MemoryHigh=1G
MemoryMax=1200M
IOWeight=20

Services can be attached to this slice simply by adding Slice=background.slice inside their unit definitions.

5. Monitoring via Pressure Stall Information (PSI)

Traditional CPU load averages conflate CPU wait with uninterruptible disk sleep and provide no insight into memory stalls. Linux PSI introduces precise stall metrics directly exposed under /proc/pressure/: 

# Inspect memory pressure
cat /proc/pressure/memory
# Output:
# some avg10=0.00 avg60=0.00 avg300=0.00 total=312415
# full avg10=0.00 avg60=0.00 avg300=0.00 total=184912

The some metric indicates the percentage of wall-clock time that at least one task was stalled waiting for memory. The full metric indicates that all non-idle tasks were stalled simultaneously (thrashing).

Real-time per-cgroup monitoring can be inspected interactively with: 

systemd-cgtop -m -p

Summary Checklist

  • Ensure boot parameters do not force cgroups v1 (modern distributions default to unified v2).
  • Define MemoryHigh alongside MemoryMax to enable proactive reclaim before OOM termination.
  • Group unprivileged batch processing into a dedicated systemd slice with reduced IOWeight and CPUWeight.
  • Monitor PSI metrics in your telemetry pipeline to catch memory contention before latency spikes occur.
